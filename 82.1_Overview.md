### Naming Scheme:
- "Dodo" = the courier that runs a "Route" between multiple "Stations", completing side node-visits along the way called "Hops"
- "Route" = the journey between multiple "Stations." Multiple station visits with each sub journey called a Hop. Scheduled or triggered by event automatic or human
- "Hop" = the movement from one station to the next. 
- "Station" = the nodes that a dodo stops at; Each station has it's own operating procedures and their own directions for moving parcels. A dodo may stop at station C en route to station F but then station C might send its own "Dodo" on a route from station C to J by way of G, H, and I 
	- "Nest" = `.mailroom` file where the `Dodo` lands with an envelope. The `Envelope` is handled by the `Station` the `Nest` is connection for the `Dodos` and the `Station`
		- Dendritic pattern for context building
- "Parcel" = The recepticle a "Dodo" moves "envelopes" to a station. Loaded at the station and put on a "Dodo"
- "Envelope" = A packet of information with a TO and a FROM, also listing the visible destinations, current route, current leg, current dodo, 
	- `envelope_id` -> Random UUID for the Envelope that was sent
	- `content_hash` -> What this content is. This should 100% be made private and only accessible by retrieving the hash through the mailroom. I built a lot of overview and front end `Stations` specifically into the JD simply so that they can point to the true destination for humans or files
- "Postcard" = An envelope sent to all top stations (1x, 2x, 3x, etc;) to be handled accordingly with the intention of dissemenating a notice; "Shut down in five minutes", "Station is moving from index (31.2-H to 31.2-B)
- "Master Index" = The master index that establishes the destinations of the routes. 

- "Lane" - Developed and named routes that run periodically; scheduled jobs. Jobs that can be planned around and resources accounted for ahead of time; jobs that every wednesday at 3, daily heavy AI jobs, builds. Has the "preparation", "event", and "completion" stages. i.e.

## Services per machine

### Pi (the hub)

- NixOS (already running)
- Tailscale
- Mailroom (Axum server) ← what we're building
- PostgreSQL ← metadata, registry, event log
- Caddy ← reverse proxy, Tailscale-only
- u9fs client ← mounts Island's storage at /storage/Library

### Island (the workhorse)

- NixOS
- Tailscale
- Ollama / LocalAI ← GTX 1080, runs 7B-13B models
- u9fs server ← exposes /storage/Orchid over 9P on Tailscale IP
- mergerfs ← pools physical drives into /storage/Orchid

### Loom (workstation)

- Obsidian vault (git synced)
- SSH / browser into Pi and Island via Tailscale

## Storage

```
Island: /storage/Orchid      (mergerfs pool — all large files)
  exposed via u9fs over Tailscale 9P

Pi: /storage/Library         (automount — Island's storage via 9P)
  Mailroom writes here when Island is online
  Mailroom queues writes when Island is offline
```

### PostgreSQL (on Pi) holds

- Registry (built from .mailroom files in vault)
- Entry metadata (id, jd_address, type, path, created_at, tags)
- Event log (every envelope routed)
- Links (relationships between entries)

### Files (on Island via /storage/Library) hold

- Actual content — markdown, media, data files
- Organised by JD address under /storage/Library/
- PostgreSQL holds the index; files are the source of truth

## Data flow

```
Obsidian (Loom)
    ↓ git push
Pi pulls vault, refreshes .mailroom registry
    ↓
Mailroom receives Envelope (HTTP)
    ↓
Route table (JD address + data type)
    ↓
Island online  → write to /storage/Library, index in PostgreSQL
Island offline → queue envelope, retry when mount returns
    ↓
AI requests → forwarded to Island's Ollama over Tailscale
```

## Vault structure

Every JD node gets three files:

- `NodeName.md` ← human overview (Obsidian-facing, Templater)
- `.mailroom` ← machine config (TOML, parsed by Mailroom)
- `.about` ← human+AI context (Markdown, read by AI)

The `.mailroom` [about] block is AI-maintained. Run `mailroom refresh <id>` to regenerate from `.about`.
